# ADR-001. Выбор клиент-серверной архитектуры веб-приложения

## Контекст и постановка задачи

Для веб-приложения «Умный планировщик питания» необходимо реализовать составление меню на неделю, просмотр и поиск рецептов, расчёт КБЖУ, формирование списка покупок и учёт продуктов, имеющихся дома. После второго раунда согласования к первой версии добавлена функция учёта сроков годности и предупреждений об их истечении (REQ-FUNC-011). Данные о меню, рецептах и продуктах должны храниться согласованно и быть доступны через единый пользовательский интерфейс.

Требуется выбрать архитектуру, которая разделит отображение информации, обработку пользовательских действий и хранение данных, а также позволит дополнять приложение новыми возможностями без переработки всех его частей.

## Драйверы решения

* Реализация основных требований SRS, включая REQ-FUNC-001, REQ-FUNC-003, REQ-FUNC-005, REQ-FUNC-008 и REQ-FUNC-011.
* Возможность развивать отдельные модули приложения без существенных изменений остальных компонентов.
* Централизованное хранение и проверка корректности данных о рецептах, меню и продуктах.
* Удобство разработки веб-интерфейса и повторного использования компонентов.
* Ограниченные сроки и бюджет учебного проекта.
* Возможность тестирования клиентской и серверной логики по отдельности.

## Рассмотренные варианты

* Клиент-серверная архитектура: React-интерфейс, серверное API и база данных PostgreSQL.
* Монолитное веб-приложение с формированием страниц на сервере и общей серверной логикой.
* Полностью клиентское приложение с хранением пользовательских данных в браузере.

## Итог решения

Выбран вариант «Клиент-серверная архитектура: React-интерфейс, серверное API и база данных PostgreSQL». React отвечает за отображение календаря питания, рецептов, списка покупок и уведомлений. Серверная часть обрабатывает запросы, выполняет расчёты и проверки, а также управляет сохранением данных в PostgreSQL. Обмен между клиентом и сервером предполагается организовать через HTTP API с передачей данных в формате JSON.

Такое разделение позволяет независимо изменять пользовательский интерфейс и бизнес-логику, а также сохранять информацию в централизованном хранилище. Конкретный серверный язык и фреймворк в рамках данного решения не фиксируются: они могут быть выбраны на следующем этапе проектирования.

### Последствия

* Хорошо, потому что интерфейс и серверную логику можно разрабатывать и проверять независимо.
* Хорошо, потому что PostgreSQL позволяет хранить связанные данные о рецептах, ингредиентах, меню и домашних запасах.
* Хорошо, потому что функцию проверки сроков годности можно добавить в серверную логику без изменения общей архитектуры.
* Хорошо, потому что отдельные компоненты React можно повторно использовать в разных разделах приложения.
* Плохо, потому что необходимы разработка и поддержка API между клиентской и серверной частями.
* Плохо, потому что размещение приложения требует настройки сервера и базы данных.
* Плохо, потому что для работы с сохранёнными данными пользователю обычно требуется соединение с сервером.

### Подтверждение

Соблюдение решения предполагается проверять при реализации проекта: компоненты React должны обращаться к серверному API, а операции с PostgreSQL должны выполняться серверной частью. Дополнительно необходимо проверить сценарии создания недельного меню, формирования списка покупок, подсчёта КБЖУ и отображения предупреждений о сроках годности. При ревью следует убедиться, что клиент не подключается к базе данных напрямую.

## Плюсы и минусы вариантов

### Клиент-серверная архитектура: React, API и PostgreSQL

* Хорошо, потому что разделены представление, бизнес-логика и хранение данных.
* Хорошо, потому что предусмотрено централизованное хранение пользовательской информации.
* Хорошо, потому что архитектура допускает постепенное добавление функций.
* Плохо, потому что необходимо согласовать и поддерживать интерфейсы обмена данными.
* Плохо, потому что развёртывание нескольких компонентов сложнее, чем у полностью клиентского приложения.

### Монолитное веб-приложение с формированием страниц на сервере

* Хорошо, потому что единая серверная кодовая база может упростить первоначальное развёртывание.
* Хорошо, потому что бизнес-логика и доступ к данным находятся в одном приложении.
* Нейтрально, потому что PostgreSQL также может использоваться в данном варианте.
* Плохо, потому что такой подход не соответствует выбранной модели интерфейса на React без дополнительных архитектурных решений.
* Плохо, потому что изменения отображения и серверной логики могут оказаться сильнее связаны друг с другом.

### Полностью клиентское приложение с хранением данных в браузере

* Хорошо, потому что не требуется собственный сервер для обработки основных действий пользователя.
* Хорошо, потому что упрощается первоначальное размещение статического интерфейса.
* Плохо, потому что сохранённые данные зависят от браузера и устройства пользователя.
* Плохо, потому что сложнее обеспечить централизованное хранение, целостность и восстановление данных.
* Плохо, потому что дальнейшее развитие приложения с синхронизацией данных потребует изменения архитектуры.
